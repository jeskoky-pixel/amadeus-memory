# Amadeus Memory Enhancer — Codex 验收

2026-10-25。开发分支：`codex/memory-enhancer`。基线：Mneme 上游 `146fa3657dbb73c0498aba969977e7c14e13684a`，导入提交 `13e6520`。本次仅修改独立开发工作树；生产插件、DSH 主配置和生产 SQLite 未切换或写入。

## 已验收的行为

- 稳定身份以 `(platform, entity_type, external_id)` 为键。同一平台、同一类型的不同 ID 即使昵称相同，也保持独立；同一 ID 更名仍解析到原 UUID。没有可靠 ID 的人物或群组不能只凭名称自动归并。
- 跨平台同类型实体默认独立，可由用户查看 dry-run 报告后手动确认关联。人物与群组不能合并；相同平台和数字 ID 在不同类型下可以分别存在。
- 旧库的确定性 QQ 群号可识别旧提取器标为 `organization` 的实体。迁移把这类实体类型修正为 `group`，把原类型写入审计证据；一个群号只建立一个有效外部身份键，重复行留作人工确认候选，不自动合并。
- 合并只建立可撤销的规范链接。确认前在写事务内重新计算属性、关系、身份、别名和阻断条件的指纹；原记忆、实体属性时间线及关系来源和权重不因合并改写。
- Tag 与实体偏好作为独立且有上限的排序信号；默认关闭或全为 1.0 时保持旧检索结果。可信经历入口要求明确来源、参与状态和 scope。
- 新的身份、偏好及经历来源接口要求服务端实际配置 `apiToken`；旧开放目录和图谱接口只返回脱敏的原有字段。开放目录搜索、图谱查询、`entity:` 搜索和普通搜索的图谱召回都只用公开名称或 UUID，不能通过查询探测私人别名或外部 ID。实体目录支持分页、搜索和真实总数，原生面板可继续加载后续实体。

## 检索与运行成本

Codex 在最终代码上复跑同一合成基准（50 条记忆、3 个查询、3 轮、每轮 20 次）：Recall@5 `0.3333 → 0.8492`，MRR `0.3333 → 1.0000`，p95 `6.25 → 9.55 ms`，数据库大小 `344064 → 475136 B`。偏好开启带来约 3.3 ms 的 p95 绝对开销；默认关闭路径由回归测试验证。该基准没有向量模型、并发、真实查询分布或后台 LLM，不能据此推断生产负载的绝对延迟和准确率。

## 部署与回滚边界

开发分支将通过独立 PR 交付，保持未合并。生产启用前先对当前 SQLite 做一致性备份，在隔离配置中设置 `apiToken` 和所需功能开关，查看迁移及重复候选；任何规范归并都须人工审阅 dry-run。代码回滚可恢复原插件版本；数据回滚使用启用前的 SQLite 备份。偏好开关关闭后不改变原 importance、遗忘、归档和 scope 规则。

## 定向质量修复与最终验收（2026-10-25）

本节覆盖上述初验，代码仍在 `codex/memory-enhancer`，PR #1 保持开放。本轮仅处理已复现的缺陷；生产 Mneme、DSH Profile、QQ Bridge 和 Life 数据没有切换或写入。

### 修复结论

- **P0 可信经历**：普通 `memory_save`、`memory_update`、面板、独立 HTTP API 和共用服务写入路径不能靠 `source=trusted_intake` 或大小写、NFKC 兼容写法铸造 `event:*`。受控 intake 只派生所声明 kind 的标签，拒绝额外事件标签。合法事件的标签由已提交 provenance 支撑，在普通更新和同标题归并后保留。读取展示与 Tag 偏好也忽略旧库中没有匹配 provenance 的事件标签。失败写入不留下半条记忆或 provenance；普通自定义 Tag 和来源描述仍可用。
- **P1 Life 幂等**：`memory_trusted_requests` 以规范化 actor 加 `request_id` 为唯一键，并记录材料内容指纹；相同请求返回原记忆和原 provenance，冲突返回 409，不同 request ID 的同标题经历保持独立。检查与写入在 `BEGIN IMMEDIATE` 事务内，包含真实重叠的双连接并发回归。无 request ID 维持旧兼容行为。
- **P1 身份连续性**：无可靠 ID 时仍不按昵称猜测人物。待确认属性和关系连同来源记忆持久保存；两个端点都被人工安全确认后，关系可以跨重启恢复一次。同名不同稳定 ID、人物/群组边界、已遗忘或已删除来源仍受阻断。持久待确认数据有大小上限；复杂歧义需人工逐条选择，属于设计取舍。

### 检索消融与运行成本

同一合成夹具、查询、Top 5、过滤条件，3 轮各 20 次；A 是导入时原 Mneme，B/C/D 使用相同扩大的候选池。延迟为本轮端到端查询 p95：

| 组别 | Recall@5 | MRR | p95 |
| --- | ---: | ---: | ---: |
| A 原 Mneme | 0.3333 | 0.3333 | 8.013 ms |
| B 仅扩大候选池 | 0.3333 | 0.3333 | 7.985 ms |
| C 候选池 + Tag 权重 | 0.8492 | 1.0000 | 11.407 ms |
| D 候选池 + Tag/实体权重 | 0.8492 | 1.0000 | 10.619 ms |
| 全 1.0 对照 | 0.3333 | 0.3333 | 7.210 ms |

这组数据中扩大候选池本身没有带来准确率增益；Tag 权重带来测得的提升，实体权重没有额外的 Recall@5/MRR 增益。D 相比 A 的 p95 多约 2.606 ms；不同轮次的毫秒差含调度噪声，不能据此解释 C/D 的细微差异。50 条合成记忆覆盖群聊噪声、低频重要人物、自身活动、无关高权重和旧重要记忆，但没有真实聊天查询分布、并发、向量模型或后台 LLM；生产准确率和绝对延迟尚未验证。详细逐查询排名在 `dsh-mneme/reports/memory-enhancer-ablation.json`。

### 生产准备与回滚

当前质量已适合进入**受控生产部署准备**，PR 不自动合并或部署。部署前对当时的生产 SQLite 做一致性备份，先在隔离 Profile 上设置专用 `memoryDir`、`apiToken` 与功能开关，检查迁移和重复身份候选，再在维护窗口启用；人工规范合并先 dry-run 再确认。出现问题时先关闭新偏好/intake 功能和插件，恢复旧插件版本；若需数据回滚，用启用前的 SQLite 一致性备份恢复。上线观察应补测真实查询的 Recall、p95、向量路径、长时间图谱增长和模型工具调用。
